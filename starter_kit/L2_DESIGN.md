# L2 设计方案：说人话的量子智能体

> L2 初始实现来自 `feature/l2-agent`，最终在 `feature/l2-integration` 与 L1/L3 集成。
> 目标：客观分 20 + 交互体验 10 = 30 分，并争取「新手引导与视觉叙事」+4 Bonus。

---

## 1. 评分驱动的设计约束

先把规则读成工程约束，避免做错方向。

| 规则 | 出处 | 对设计的硬约束 |
|---|---|---|
| 评测器直接调用 `agent_chat(prompt) -> str` | 提交契约 | 全部客观分逻辑必须能在**无 UI、无网络（除模型服务）**下跑通 |
| 必须至少一次有效模型调用，否则该 case 不具备得分资格 | L2 判定 | **禁止**为了稳态而走「纯本地模板、跳过 LLM」的捷径 |
| 必须读 `LOOMQ_LLM_*` 环境变量 | L2 运行时规范 | 不得硬编码 base_url / key / model |
| 每 case 限时 120 秒 | `l2_policy.json` | 自验重试循环必须有**总时间预算**，不能无限重试 |
| 评测用未公开 prompt 变体 | 反作弊 | 不能靠关键词匹配；措辞、比特数、目标态都会变 |
| 交互分**仅在客观分 ≥ 12 时计入** | L2 判定 | **客观分优先**，UI 是第二阶段 |
| 评测环境不保证访问模型服务以外的网络 | 多处 | UI 必须本地自包含，禁 CDN／外部字体 |

**最重要的一条**：交互分有 ≥12 的门槛。所以工作顺序必须是**先做稳客观分，再做 UI**，不能反过来。

---

## 2. 三类任务与判定方式

评测注入三类任务，判定方式完全不同，这决定了要分流处理：

| 任务 | 示例 | 判定 | 关键点 |
|---|---|---|---|
| **意图生成** | 「生成 3 比特 GHZ 态并全测量」 | 产物 QASM 经无噪声模拟，**Fidelity ≥ 0.97** | 输出必须含可解析 QASM |
| **代码纠错** | 「想制备贝尔态，但这段报错：`H q[0]; CX q[0] q[1]`」 | 修复产物须在语义上实现**prompt 声明的目标态**并通过 Fidelity | 以*声明意图*为准，不是以坏代码为准 |
| **智能选后端** | 「15 比特、零排队，选哪个平台？」 | 回复须含**规范后端标识**，按官方能力表核对唯一正确答案集 | 输出必须含 `backend_capabilities.json` 里的 `id` 原文 |

前两类是「QASM 正确性」问题，第三类是「查表 + 约束满足」问题。**第三类根本不需要 LLM 来算答案**——但仍须完成一次有效模型调用才具备得分资格。

## 3. 核心架构

```
agent_chat(prompt)
      │
      ├─ 1. 分类 (classify)          ── LLM 一次调用，同时产出结构化意图
      │
      ├─ 2. 分流
      │     ├─ 生成/纠错 ─→ 生成 QASM ─→ ★自验闭环 ─→ 通过?  ─→ 输出
      │     │                              ↑          │否
      │     │                              └──重试────┘ (带错误反馈)
      │     │
      │     └─ 选后端 ─→ 本地约束求解 (backend_capabilities.json) ─→ 输出 id
      │
      └─ 3. 兜底 (fallback) —— 预算耗尽时输出当前最佳候选，绝不抛异常
```

### 3.1 自验闭环是 L2 的胜负手

题面明说这是「推荐工程方案」。我们**已经有 L1 的全部零件**，成本极低：

```python
from starter_kit.qasm_parser import parse_qasm
from starter_kit.simulator import simulate, result_probabilities
```

`simulate()` 返回完整态矢量（`list[complex]`），可以算**真 fidelity**，而不是只比对采样计数：

```
fidelity = |⟨ψ_target | ψ_generated⟩|²
```

闭环逻辑：

1. LLM 生成 QASM
2. `parse_qasm()` —— 语法层拦截。解析失败 → 把**解析器的报错原文**回灌给 LLM 重试
3. `simulate()` —— 语义层校验。对可识别目标态（GHZ / Bell / W / 均匀叠加等）算 fidelity
4. fidelity < 0.97 → 带「实际得到的分布 vs 期望分布」重试
5. 通过 → 返回

第 2 步和第 4 步的**错误反馈**是关键：不要只说「错了，重试」，要把具体报错和实际概率分布交给模型。这是把通过率从 ~60% 拉到 ~90% 的部分。

### 3.2 目标态识别

自验需要知道「期望态是什么」。这本身也交给 LLM 在第 1 步以结构化形式产出：

```json
{
  "task": "qasm | select_backend | explain",
  "target_state": "ghz | bell | w | uniform | custom",
  "num_qubits": 3,
  "qasm": "完整 OpenQASM 2.0 或 null",
  "answer": "纯概念问题的大白话回答或 null",
  "constraints": {"min_qubits": 15, "no_queue": true}
}
```

对 `custom` 或识别不出的情况，降级为「只做语法校验 + 门级合理性检查」，不强行算 fidelity——**宁可不拦截，也不要误杀正确答案**。

### 3.3 选后端：本地求解，不靠模型算

按 `backend_capabilities.json` 做确定性过滤，避免模型算错：

```
候选 = [b for b in backends if b.max_qubits >= 需求比特数]
若要求零排队 → 过滤 queue == "none"
若要求免费   → 过滤 cost == "free"
若要求免账号 → 过滤 requires_account == false
排序：qpu 优先级 / 比特数余量 / 成本
```

例：15 比特 + 零排队 → `max_qubits ≥ 15` 且 `queue == "none"` → `spinq_taurus_simulator`(24)、`originq_local_simulator`(30)、`braket_local_simulator`(25)。题面示例答案是 `braket_local_simulator`，且能力表注明它是「评测推荐默认模拟器」——**优先级排序需要据此调**，并在输出中列出备选 id 以提高命中「正确答案集」的概率。

> 注意：此类 case 仍须完成一次有效模型调用才具备得分资格。分类步骤天然满足这一点——**不要为省时间跳过它**。

### 3.4 时间预算

120 秒硬限。分配：

| 阶段 | 预算 |
|---|---|
| 分类调用 | ~15s |
| 生成 + 自验（每轮 ~20s） | 最多 3 轮 ≈ 75s |
| 兜底与输出 | ~10s |
| 安全余量 | ~20s |

用**单调时钟**统一计时，每轮开始前检查剩余预算，不够就直接输出当前最佳候选。**`agent_chat` 永远不抛异常**——异常等于 0 分，输出一个不完美的 QASM 至少有机会拿分。

### 3.5 输出格式

评测取「返回文本」判定，所以文本里必须**同时**含人类可读解释和机器可提取产物。QASM 放进 ```` ```qasm ```` 围栏，后端 id 用原文标识符。宁可冗余，不要缺失。

## 4. 模块划分

新增文件均放在 `starter_kit/` 下（评测根目录），`adapter.py` 只做薄转发：

```
starter_kit/
├── adapter.py              # 改：agent_chat 转发到 agent 包
└── agent/
    ├── __init__.py
    ├── core.py             # 编排、时间预算、重试与兜底
    ├── prompts.py          # 结构化系统提示词
    ├── verifier.py         # ★ 自验：parse + simulate + fidelity
    ├── backends.py         # 选后端约束求解
    ├── presenter.py        # 电路图与零基础解释
    ├── server.py           # 本地 HTTP 入口
    └── ui.html             # 自包含交互界面
```

`verifier.py` 复用 L1 的 `qasm_parser` / `simulator`，不重写。

## 5. UI：Win98 皮 + 现代交互内核

**定位**：视觉上全 Y2K，交互流程上是引导式现代 UX。评委看的是「零物理背景用户能否用」，怀旧是加分的叙事外衣，不能变成使用障碍。

### 5.1 技术选型

- **单文件自包含 HTML**，零 CDN、零外部字体（评测环境不保证外网；题面 `LoomQ-赛题.html` 本身就是这个规格，与仓库风格一致）
- 后端：Python `http.server` 起本地服务，调用同一个 `agent_chat`
- 示例按钮只提交自然语言，不包含预制答案；意图由模型按结构化 Prompt 判断
- **UI 与客观分完全解耦**——UI 挂了不影响 20 分

### 5.2 关键界面

```
┌─ LoomQ 量子助手 ─────────────────────[_][□][X]┐
│ 文件  编辑  查看  帮助                          │

3. 「我要跑 15 比特、不想排队」→ 得到后端推荐与理由

## 7. 风险

| 风险 | 应对 |
|---|---|
| 隐藏变体措辞超出预期 | 分类步骤不做关键词匹配，交给 LLM 按 JSON Schema 和意图优先级结构化输出；用独立变体测试验证，不内置评分样例答案 |
| 目标态识别失败导致误杀正确答案 | 识别不出时**降级为只校验语法**，不强行 fidelity 拦截 |
| 120 秒超时 | 单调时钟 + 每轮预算检查 + 兜底输出 |
| 模型返回非规范 QASM（含 markdown/解释文字） | 提取器容错：围栏优先，退化为正则扫 `OPENQASM` 起始段 |
| 组委会模型服务异常 | 题面已说明会复评；我方只需保证不因异常抛出未捕获错误 |
| UI 抢占客观分工期 | 客观分未稳定（阶段 E 前）不动 UI |
